# 할 일 관리 앱 구현 계획

Status: **pending approval**
Source: `docs/PRD.md`
Mode: Interview → Direct (consensus 미사용)

## 1. Requirements Summary

할 일(일일) → 주간 계획 → 1년 목표 계층을 갖는 단일 사용자 웹 앱. 칸반 보드(todo/doing/done)에서 Drag & Drop으로 상태를 바꾸면 주간·연간 진행률이 자동 반영된다.

### 확정된 결정 (PRD "확인 필요 사항" 해소)

| 항목 | 결정 |
|---|---|
| 플랫폼 | 데스크톱 브라우저용 웹, Next.js (App Router) + TypeScript. 모바일 전용 UI와 터치 드래그는 MVP 범위 밖 |
| 저장소 | 로컬 MongoDB |
| 로그인 | 없음 (단일 사용자). 모든 문서에 `userId` 필드를 미리 두어 이후 인증 추가에 대비 |
| 배포 | MVP는 로컬 실행 전용 |
| 상위 항목 삭제 | 하위가 있으면 삭제 차단 (409). 아래 P0 요구사항 참고 |

### P0 요구사항: 상위 항목 삭제 정책

PRD의 필수 계층 연결을 지키기 위해 연쇄 삭제와 연결 해제를 모두 하지 않는다.

| 대상 | 조건 | 동작 | 진행률 영향 |
|---|---|---|---|
| 목표 | 주간 계획이 1개 이상 | 409와 하위 개수 안내, 데이터 변경 없음 | 없음 |
| 목표 | 주간 계획 없음 | 삭제 | 다른 목표에 영향 없음 |
| 주간 계획 | 할 일이 1개 이상 | 409와 하위 개수 안내, 데이터 변경 없음 | 없음 |
| 주간 계획 | 할 일 없음 | 삭제 | 가중치가 0이므로 목표 진행률 불변 |
| 할 일 | 항상 | 삭제 | 소속 주간 계획과 목표 진행률이 다음 조회부터 재계산됨 |

하위가 있는 상위 항목을 지우려면 할 일을 다른 주간 계획으로 옮기거나 삭제한 뒤 진행한다. 할 일을 옮기면 이전·새 주간 계획과 각 목표의 진행률이 함께 바뀐다. 진행률은 조회 시 계산하므로 별도 재계산 코드는 없다.

### 성공 지표

단일 사용자 MVP라 주간 활성 사용자 수는 의미가 없어 아래 두 지표로 대체한다. 둘 다 저장된 데이터로 계산하며 별도 분석 도구는 쓰지 않는다. 목표값은 MVP 초기값이고 4주 사용 후 조정한다.

| 지표 | 정의 | 목표 |
|---|---|---|
| 주간 계획 유지 | 할 일이 1개 이상 연결된 주간 계획이 있는 주의 연속 횟수 | 4주 연속 |
| 할 일 완료율 | 주간 진행률(가중치 기준)의 최근 4주 평균 | 60% 이상 |

### 비기능 요구사항

- **성능** (로컬 환경, 할 일 1,000개 기준): 드래그 후 화면 반영 100ms 이내, API 응답 p95 300ms 이내, 보드 첫 로드 1초 이내.
- **상태 변경 실패**: 네트워크 오류, 5xx, 5초 타임아웃이면 카드와 진행률을 이동 전 값으로 되돌리고 오류 메시지를 보인다. 자동 재시도는 하지 않는다.
- **연속 이동**: 같은 카드의 `PATCH`는 순서대로 하나씩 보내, 늦게 도착한 응답이 최신 상태를 덮어쓰지 않게 한다.
- **동시 수정**: 여러 탭의 수정은 마지막 저장이 이긴다(last-write-wins). 다른 탭에서 삭제된 할 일을 옮겨 404가 오면 카드를 없애고 안내한다.

### 설계 결정 (이 계획에서 정함, 이의 있으면 변경)

- **진행률은 저장하지 않고 조회 시 계산한다.** 상태 변경·추가·삭제마다 재계산하는 코드를 흩뿌리면 어긋나기 쉽다. 단일 사용자 규모에서는 aggregation 비용이 무시할 수준이다. PRD의 "자동 갱신"은 항상 최신 값을 반환하는 것으로 충족한다.
- 주간 계획 가중치 = 소속 할 일 가중치 합이므로, 1년 목표 진행률 = `done 가중치 합 / 전체 가중치 합` (소속 모든 주간 계획의 할 일 기준)으로 수학적으로 동일하다. 구현은 이 식 하나로 한다.
- 가중치는 1 이상이므로 가중치 합이 0인 경우는 할 일이 없을 때뿐이다. 이때 진행률은 0으로 반환하고 화면에 `0%`로 표시한다. 할 일이 없는 주간 계획은 가중치가 0이라 목표 진행률에 영향을 주지 않는다.
- 할 일 날짜는 연결된 주간 계획의 시작일~종료일 범위 안이어야 한다. 위반 동작은 다음과 같다.
  - 할 일 생성·수정(날짜 또는 주간 계획 변경 포함): 400을 반환하고 저장하지 않는다.
  - 주간 계획 기간 수정으로 기존 할 일이 범위를 벗어나는 경우: 409를 반환하고 저장하지 않는다.
- MongoDB 트랜잭션(replica set)이 필요 없는 구조로 유지한다.

## 2. RALPLAN-DR 요약

**Principles**: 계층 무결성 우선 / 진행률은 파생 값 / 낙관적 UI와 서버 단일 진실 원천 / MVP는 P0 먼저, P1은 얹는 형태

**Decision Drivers**: (1) 진행률 정합성 (2) 드래그 반응성 (3) 단일 사용자 MVP 범위

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 조회 시 계산 (채택) | 정합성 보장, 코드 단순 | 목록이 커지면 집계 비용 증가 |
| B. 변경 시 저장 필드 갱신 | 읽기 빠름 | 갱신 누락 시 값이 어긋남, 이동·삭제 경로마다 로직 필요 |

B는 데이터가 수만 건이 되기 전에는 이점이 없어 기각한다.

## 3. 데이터 모델 (MongoDB)

```
goals { _id, userId, title, year, createdAt }
weeks { _id, userId, goalId, title, startDate, endDate, createdAt }
tasks { _id, userId, weekId, title, date, weight(1-5, 기본 1),
        status('todo'|'doing'|'done', 기본 'todo'), order, createdAt, updatedAt }
```

인덱스: `weeks.goalId`, `tasks.weekId`, `tasks.{weekId,status,order}`, `tasks.date`

## 4. Acceptance Criteria

1. 목표·주간 계획·할 일 각각 생성/수정/삭제 API와 화면이 동작한다.
2. 할 일 생성 시 `weekId` 없이는 400, 주간 계획 생성 시 `goalId` 없이는 400을 반환한다.
3. 가중치가 1~5 정수가 아니면 400, 생략하면 1로 저장된다. 신규 상태는 `todo`다.
4. 카드를 다른 컬럼으로 드래그하면 화면이 즉시 바뀌고 `PATCH`로 저장되며, 새로고침 후에도 유지된다. 저장 실패(네트워크 오류, 5xx, 5초 타임아웃) 시 카드와 진행률이 이동 전 값으로 되돌아가고 오류 메시지가 보인다.
5. 가중치 [2, 3] 두 할 일 중 가중치 2를 done으로 바꾸면 주간 진행률이 40%로 보인다.
6. 주간 계획 A(가중치 합 5, done 2)와 B(합 5, done 5)가 한 목표에 연결되면 목표 진행률은 70%다.
7. 할 일을 삭제하면 위 진행률이 새로고침 없이 재계산된 값으로 보인다.
8. 하위가 있는 목표/주간 계획 삭제는 409와 사유 메시지, 하위 개수를 반환하고 데이터와 진행률이 변하지 않는다. 하위가 없으면 삭제되고, 빈 주간 계획을 삭제해도 목표 진행률은 그대로다.
9. 목표 → 주간 계획 → 할 일 순서로 계층 조회 화면이 있다.
10. 할 일이 없는 주간 계획·목표의 진행률은 `0%`로 표시되고 오류가 나지 않는다. 할 일이 없는 주간 계획을 목표에 추가해도 목표 진행률은 변하지 않는다.
11. 연결된 주간 계획 기간 밖의 날짜로 할 일을 생성·수정하면 400을 반환하고 저장되지 않는다.
12. 주간 계획 기간을 줄여 기존 할 일이 범위를 벗어나면 409를 반환하고 저장되지 않는다.
13. 할 일을 다른 주간 계획으로 옮기면 이전·새 주간 계획과 각 목표의 진행률이 모두 바뀐다.
14. 같은 카드를 연속으로 옮겨도 마지막 위치가 저장되고, 다른 탭에서 삭제된 할 일을 옮기면 카드가 사라지며 안내가 보인다.
15. 할 일 1,000개 기준으로 비기능 요구사항의 성능 목표를 충족한다.
16. (P1) 진행 바, 일일/주간/연간 필터, 미완료 할 일 다음 주 이동, 달성 현황 요약 화면.

## 5. Implementation Steps

### Phase 0 — 기반
1. Next.js + TypeScript + Tailwind 초기화, ESLint/Prettier 설정. (`../02_wkbae`의 `.prettierrc`, `eslint.config.mjs`를 참고해 맞춘다.)
2. `.env.example`에 `MONGODB_URI`. `lib/db.ts`에 연결 싱글톤(개발 서버 핫리로드 시 중복 연결 방지).
3. `docs/CLAUDE.md`(현재 빈 파일)에 스택·명령어·규칙 기록.

### Phase 1 — 도메인과 진행률 (테스트 우선)
4. `lib/progress.ts`: 순수 함수 `calcProgress(tasks)`. 단위 테스트로 AC 5, 6, 10을 먼저 작성한다.
5. `lib/validation.ts`: zod 스키마(가중치, 상태, 날짜 범위).
6. `lib/repo/*.ts`: goals/weeks/tasks 저장소. 삭제 시 하위 존재 검사(AC 8), 할 일 날짜와 주간 계획 기간 검사(AC 11, 12).

### Phase 2 — API (Route Handlers)
7. `app/api/goals`, `app/api/weeks`, `app/api/tasks` CRUD. 응답에 계산된 progress 포함.
8. `PATCH /api/tasks/:id`로 status·order 변경. 단일 엔드포인트로 DnD와 폼 수정을 모두 처리.

### Phase 3 — UI (P0)
9. 목표 목록/생성, 목표 상세(주간 계획 목록), 주간 상세(칸반 보드).
10. 칸반 보드: `@dnd-kit/core`로 3컬럼. 낙관적 업데이트 후 실패 시 롤백(AC 4). 카드별 `PATCH` 순차 전송과 404 처리(AC 14).
11. 할 일 생성/수정 모달(제목, 날짜, 가중치, 주간 계획).
12. 진행률 숫자 표시. 삭제 차단 시 안내 메시지(AC 8).

### Phase 4 — P1
13. 진행 바 컴포넌트, 기간 필터, 달성 현황 요약 페이지.
14. 미완료 할 일 다음 주 이동: 다음 주 계획이 없으면 생성 여부를 묻는다. 날짜는 7일 뒤로 옮기고, 새 주간 계획 기간을 벗어나면 가장 가까운 시작일 또는 종료일로 맞춘다.

### Phase 5 — 마무리
15. E2E, 접근성(키보드 드래그), README.

## 6. Risks and Mitigations

| 위험 | 대응 |
|---|---|
| 낙관적 업데이트와 서버 값 불일치 | 응답으로 받은 progress로 화면을 덮어쓰고, 실패 시 롤백 |
| 드래그 순서(`order`) 충돌 | 컬럼 내 순서는 P0에서 정렬 기준만 `order`, 재배치는 마지막 위치 삽입으로 단순화 |
| 하위 존재 검사와 삭제 사이에 하위가 생겨 고아 데이터 발생 | 트랜잭션 없이 단일 사용자 전제로 허용. 인증·다중 사용자 도입 시 재검토 |
| 주 경계·시간대로 날짜 범위 검증 오류 | 날짜는 `YYYY-MM-DD` 문자열로 저장하고 비교 |
| "다음 주 이동" 시 다음 주 계획 부재 | 위 14번에서 생성 여부를 명시적으로 확인 |
| 인증 없이 배포 시 데이터 공개 | 로컬 전용으로 시작. 공개 배포 전 인증 추가를 Follow-up에 명시 |
| 대량 데이터 시 집계 느림 | 인덱스로 시작, 문제 시 옵션 B(저장 필드)로 전환 |

## 7. Verification Steps

- `npm test`: 진행률·검증 단위 테스트가 AC 3, 5, 6, 10을 통과한다.
- API 통합 테스트(인메모리 MongoDB): AC 2, 8, 11, 12, 13, 그리고 상태 변경 후 진행률 값을 확인한다.
- E2E(Playwright): 목표 → 주간 → 할 일 생성 → 드래그 → 진행률 확인 → 새로고침 후 유지(AC 4~7). 요청 실패를 모의해 롤백을 확인하고, AC 14를 확인한다.
- 성능: 할 일 1,000개를 시드한 로컬 환경에서 AC 15의 수치를 측정한다.
- `npm run lint`, `tsc --noEmit`, `npm run build`가 오류 0이다.
- 실제 브라우저에서 보드를 열어 드래그와 진행률 변화를 눈으로 확인한다.

### 완료 기준 (MVP)

- P0인 AC 1~15와 위 검증 항목을 모두 통과한다.
- 건너뛴 테스트(`test.skip`, `.only`)와 미구현 분기가 없다.
- README의 절차대로 로컬에서 앱을 실행할 수 있다.
- 성공 지표는 출시 조건이 아니라 MVP 완료 후 4주간 측정한다.
